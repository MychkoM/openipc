### 2a. Image orientation — MUST be rotated 180°
The E975 sensor is mounted upside down: the picture needs a 180° turn = mirror + flip. Required in `/etc/majestic.yaml`:
```yaml
image:
  mirror: true   # horizontal
  flip: true     # vertical (together = 180°)
```
(set by the owner 2026-10-16; fresh installs default to false/false → check after reflash)

### 4a. Datasheet vs reality — the 1080p fps ceiling (chip level, 2026-10-17)

Official Hi3518EV200 Brief Data Sheet (HiSilicon, Issue 02, 2015-12-28; saved as `openipc/Hi3518EV200_Brief_DataSheet.pdf` + .txt):
- **VENC**: H.264 ≤ 2 Mpix; realtime profile = **720p@30 + VGA@30 + QVGA@30** + 720p@1 fps JPEG snapshot (total ≈ 39 Mpix/s); JPEG snapshot 2 Mpix@5 fps; encode fps 1/16–30.
- **VI**: 8/10/12/14-bit DVP, pad clock ≤ 100 MHz, input ≤ 2 Mpix (1920×1080). A 1080p@30 sensor (~74 MHz pixel clock) fits — VI is NOT the bottleneck (verified live: sensor honestly delivers every rate tested).
- **DDR2**: embedded 512 Mbit 16-bit @ 360 MHz ≈ 1.44 GB/s. CPU: ARM926@540 (live cpuinfo: ARM926EJ-S rev 5; OpenIPC kernel 4.9.37; MMZ 32 MB).

The 1080p ceiling, three levels:
1. **Passport: 1080p@15 fps** (31 Mpix/s single-stream profile). Third-party board vendor **XSTRIVE 迅思维科技** states it explicitly for their EV200 encoding board: «1280x960@30fps or **1920x1080@15fps** H.264 HP encoding» — https://www.xstrive.com/doc-1323.html
2. **Calculated multi-stream budget: ~18–19 fps** (39 Mpix/s ÷ 2.07 Mpix/frame; ~17.4 with the 704×576 substream running).
3. **Empirical: 20 fps** (41.5 Mpix/s) — only pre-26.09 majestic binaries stream it (see §4 ladder); post-25.09 binaries cap 15–16.8.

**Why the cap (majestic 25.09→26.09 regression, root cause):** the majestic upstream repo is CLOSED; `general/package/majestic/majestic.mk` pulls a FLOATING `majestic.<family>.<variant>.master.tar.bz2` from S3, so every nightly silently ships whatever closed-source master was built that day — the guilty change (single day, 69671d4 2026-09-25 → 17ec3ed 2026-09-26) is invisible in the firmware repo. On 01.10+ the JPEG channel is FPS-NEUTRAL (A/B 151/151) — the 21.09 mechanism «extra venc channel unlocks video0 fps» was REMOVED and replaced by an **integer drop-fraction limiter** that pulls output toward the datasheet profile (~34–35 Mpix/s main channel with the substream running). Sensor-rate sweep on the native 16.10 binary (count_frames-verified): `Isp_FrameRate` 15→12 (keep ¾), 17→13 (¾), 20→15 (¾ — the ONLY regular cadence, clean 1-of-4 drop, PTS 50/50/100), 24→15 (⅝), **25→16.8 (⅔ — the fps maximum of the native binary)**, 30→15 (½). Output is non-monotonic (peak at 25); every rate ≠ 20 trades fps for jitter. I.e. the regression is best read as majestic CONFORMING the output to the chip's documented profile: 1080p@20 = an above-datasheet mode only the old binaries allowed.


**How the cap was chased (and what it was NOT):** 16.10 upstream → 15; 10.10 fork → 15; 21.09 upstream (7ca8b7e) → 15; kernel-only swap to the user's own 21.09 kernel build (19:45, from .132 mtd2, `sysupgrade --kernel=FILE`) → still 15 — so not the kernel. env identical (`osmem=32M`, MMZ 32 MB, same cmdline on .132/.243) — not env. rootfs diff (.132 bisect vs upstream 21.09): only the WiFi stack (mt7601sta bisect), gc2033 files baked into the fork build, busybox rebuild noise; venc/rc/h264e/vpss/viu .ko identical (104733ec…) — not rootfs, not modules. majestic binary d4521bb on both 20 fps and 15 fps results — not the binary version. The only config delta vs .132: **jpeg off** (we disabled it "to free the SoC budget" during the fps hunt — that very disable created the cap). .132 has always run with jpeg-on (default) → always honest 20. The earlier "kernel pixel budget ≈31 Mpix/s" theory is RETRACTED (720p@20 was uncapped at jpeg-off, which contradicts a pixel budget; the numbers coincided by accident).

### 5. Motion input + pinmux map (updated 2026-10-17)
- **Motion input = pad 0, alt1 = IR_IN** (IR photodiode): an OPTICAL IR-activity detector, NOT a pyroelectric PIR and NOT sensor I2C. Verified live: `ipctool gpio scan` (180 s, hand waving in front of the camera) — pad-0 bit toggled 6× from reflected IR; no other unknown pad toggled during motion → there is no separate PIR pad. The SAR-ADC path exists on the chip (4-channel, per datasheet) but is NOT exposed on this firmware (no IIO, no driver, no device node; the EV200 register base is not in the available docs — the 0x200B0000 base found online belongs to the different hi3518e-720p chip; do not poke blind). majestic exposes no software motion keys (the IVE smart-analysis engine exists per datasheet but is unused).
- **Sensor I2C = I2C0 on pads 16 (SCL) + 17 (SDA), mux=2** — set by the load_hisilicon gc2033/sc2035 case (`0x200f0040=2 I2C0_SCL`, `0x200f0044=2 I2C0_SDA`); live registers confirmed. The old «pin 0 = sensor I2C SDA» attribution (from the 2026-10-16 night incident) is RETRACTED: the incident's mux-forcing did cascade into sensor-I2C timeouts (mechanism unclear), but the pinmap shows the sensor bus on 16/17, not 0.
- **pinmux map, pads 0–31** (live mux registers `0x200F0000 + 4×pad`, devmem-read 2026-10-17):
  - alt (mux≠0): **0**=IR_IN (1), **2**=TEMPER_DQ (1), **4**=SENSOR_CLK (1), **5**=SENSOR_RSTN (1), **6**=FLASH_TRIG (1), **7**=SHUTTER_TRIG (1), **8–11, 13–15**=VI_DATA9–15/VI_VS/VI_HS DVP sensor bus (1/2), **16/17**=I2C0_SCL/I2C0_SDA (2), **26**=MDIO (1), **27**=I2C0_SCL alternate point (1), **31**=I2C1_SCL alternate point (1).
  - GPIO (mux=0): **1** (IR LED), 3, 12, **18–25** (RMII/EPHY ethernet), 28 (I2C0_SDA alternate, unused), 29, 30. Pads 32+ (LED 60/61, lightSensor 62, IRCUT 64/65) as per §1.
- **CRITICAL tool warning**: `ipctool gpio mux <pad>` prints its OWN static name table (bracketed entry = table default), NOT the live mux register — it showed [GPIO0_0] on pad 0 while the register was 1 (IR_IN), and [RMII_CLK] on pad 16 while the register was 2 (I2C0_SCL). The live value is only `devmem 0x200F0000+4×pad`; the authoritative name↔mux mapping lives in the load_hisilicon comments. `ipctool gpio scan` DOES work as a live monitor (group register snapshots + printed deltas on change) but only sees non-masked group bits (masked `xxx` bits in Gr1–Gr2 are alt pads it cannot sample).
- **Mux lesson (2026-10-16 incident, kept)**: never force an unknown pad's mux to GPIO — the pad-0 forcing cascaded into sensor-I2C fifo timeouts («wait last i2c fifo is empty timeout») and a dead stream; recovery required mux restore + REBOOT (the I2C controller hang survives a restart). sysfs GPIO on a muxed pad reads/writes the gpio register, NOT the physical pad.
- **Deployed**: `/usr/bin/red_motion.sh` (2026-10-17, nohup, not in init — dies on reboot) — **owner-verified superior**: on a pad-0 IR impulse the RED status LED (pad 60) blinks 1 s ON / 1 s OFF, extending on new impulses, dark 3 s after the last one; log `/tmp/red_motion.log`; uses `/usr/bin/led`; kit copy `sensors-gc2033/red_motion.sh` (md5 125e4ee5). Supersedes the old `/usr/bin/pir_monitor.sh` motion reaction (that one died in the reboots; its IR-LED blink + `/tmp/pir.log` role is covered). **Status: STOPPED by owner 2026-10-17 19:14 (process killed, LED forced dark) — the file is KEPT in the overlay**; restart with `nohup /usr/bin/red_motion.sh &`.
- **Sensitivity test (2026-10-17 19:04–19:07, owner-driven enter/exit scene)**: 20 Hz sampling of the pad-0 data register for 140 s. Result: 57 s of empty room = **0 events (zero false positives)**; a single short impulse (<1 s) at 19:05:47 matched the owner's ENTRY into the room; the following exit produced NO impulse. Combined with the earlier hand-waving test (6 toggles/180 s right in front of the camera): pad-0 IR_IN reacts with **single short impulses only to intense/close IR changes — walking through the room is caught ~50% of the time**. Verdict: usable as a clean low-false-positive IR-activity hint, NOT a reliable pass-through motion detector; for reliable motion use host-side stream analysis (ffmpeg scene detect) or ONVIF CellMotionEngine.
